# ORMD Cleanup and Obsidian Plugin Plan

Date: 2026-05-14

## Current Project State

The project is a Python CLI plus format/spec experiments for Open Relational Markdown. The strongest reusable pieces for an Obsidian plugin are:

- `ormd_cli/src/ormd_cli/parser.py`: parses the version tag, YAML front matter, body, and inline semantic links.
- `ormd_cli/src/ormd_cli/schema.py`: defines the front-matter shape and approved link relationships.
- `ormd_cli/src/ormd_cli/validator.py`: validates required fields, links, anchors, assets, and legacy metadata blocks.
- `ormd_cli/src/ormd_cli/html_generator.py`: renders ORMD-flavored Markdown to HTML.
- `spec0.1.md`: the clearest current statement of the `.ormd` 0.1 format.

## Obsidian Plugin MVP

Goal: make `.ormd` files feel like Markdown files in Obsidian, with ORMD-aware validation and relationship rendering.

MVP capabilities:

- Open `.ormd` files in Obsidian as editable Markdown-like text.
- Show a status-bar validation state for the active `.ormd` file.
- Add commands:
  - `ORMD: Validate current file`
  - `ORMD: Update generated metadata`
  - `ORMD: Insert semantic link`
  - `ORMD: Open relationship panel`
- Render `[[link-id]]` references from `links:` front matter as clickable relationships in reading view.
- In Live Preview, decorate semantic inline links and undefined `[[link-id]]` references.
- Provide a side panel listing title, authors, links, unused links, undefined references, and broken anchors.

Non-goals for the first plugin:

- ZIP `.ormd` package editing.
- Cryptographic signing.
- Real-time collaboration.
- PDF/Word/Excel conversion.
- Full visual replacement for the existing HTML renderer.

## Suggested Plugin Architecture

Recommended repo layout:

```text
obsidian-ormd/
  manifest.json
  package.json
  tsconfig.json
  esbuild.config.mjs
  src/
    main.ts
    format/
      parser.ts
      schema.ts
      validator.ts
      serializer.ts
    obsidian/
      extensions.ts
      postprocessors.ts
      commands.ts
      relationship-panel.ts
    styles.css
  tests/
    fixtures/
```

Core classes/modules:

- `OrmdPlugin`: Obsidian plugin entry point.
- `OrmdParser`: pure TypeScript parser for version tag, YAML front matter, body, inline semantic links, and `[[link-id]]`.
- `OrmdValidator`: pure TypeScript validator with line-oriented diagnostics.
- `OrmdSerializer`: updates front matter without reformatting the whole document when possible.
- `RelationshipPanel`: sidebar view for relationship graph/list.
- `OrmdEditorExtensions`: CodeMirror decorations and lint markers.
- `OrmdMarkdownPostProcessor`: reading-view rendering for semantic links.

Implementation sequence:

1. Scaffold from the Obsidian sample plugin and verify `npm run dev` emits `main.js`.
2. Register `.ormd` with the Markdown view if the current Obsidian API/types support it cleanly; otherwise document the fallback path.
3. Port parser and validator with fixtures before adding UI.
4. Add command-palette validation and status-bar feedback.
5. Add reading-view postprocessor for `[[link-id]]`.
6. Add Live Preview decorations for `[[link-id]]` and inline semantic links.
7. Add metadata update command.
8. Add relationship panel.

## Open Design Decisions

- Should `.ormd` files use Obsidian's native Markdown view or a custom view? Recommendation: native Markdown view first; custom view only for packaged `.ormd` archives later.
- Should Obsidian front matter treat ORMD metadata as note properties? Recommendation: yes where compatible, but keep ORMD-specific link semantics under `links:`.
- Should `[[link-id]]` overlap with Obsidian wiki links? Recommendation: treat ORMD link IDs separately inside `.ormd` files only, because Obsidian already owns `[[Note Name]]` semantics in normal Markdown.
- Should `.ormd.zip` be supported? Recommendation: read-only package inspection after the plain-text `.ormd` MVP works.
